## 3. 路径可移植性

### 3.1 推荐主方案：新 manifest 使用相对路径

Pipeline 写 manifest 时，将位于 `pipeline_output_root` 内的文件统一写成相对路径：

```text
teachers/<geometry>/<condition>/budgets/budget_007000/target_mesh.vtk
```

Adapter 始终用：

```text
pipeline_output_root / relative_path
```

优点：数据目录整体移动后仍有效；路径协议简单。

需要额外再次运行 tet_work/dataest-pipeline/ 的配置，让 dataest-pipeline/output/ 目录下的所有数据变成新的相对路径

需要处理：`geometry_artifact_paths.source_path` 可能位于 output root 外，应允许独立的 geometry source root 或路径映射。

### 3.2 兼容旧数据：根目录重定位（不推荐）

为 adapter 增加显式配置，而不是猜测路径：

```yaml
path_relocation:
  enabled: true
  old_root: D:/SITP/tet_work/dataest-pipeline
  new_root: C:/Users/24848/Desktop/tet_work/dataest-pipeline # 这是在另一台机器上的路径
```

解析顺序建议：

1. 相对路径：相对 `pipeline_output_root` 解析。
2. 绝对路径且存在：直接使用。
3. 绝对路径不存在且匹配 `old_root`：替换为 `new_root`。
4. 仍不存在：**明确报错**，并记录原因。

### 3.3 备选方案：一次性 manifest 迁移工具（不推荐）

提供只处理 JSON 路径字段的迁移命令，输出新 manifest，不原地覆盖旧文件。

适合当前数据快速恢复，但不应替代 pipeline 后续写相对路径的根治方案。

> **额外思考提醒：** 路径字段不仅出现在顶层，还可能嵌套在 `geometry_artifact_paths`、`teacher_metadata.adaptive_error_history` 等对象中。训练 adapter 当前只消费部分字段，不应无差别替换所有字符串；应先定义“数据协议中哪些字段是路径”。

### 3.4 测试

- 相对路径 fixture。
- 旧绝对路径 + relocation fixture。
- 绝对路径本身存在。
- 路径失效且 policy=fail。
- 将 fixture 根目录复制/移动后重新加载。

## 4. 错误诊断与数据审计

### 4.1 当前问题

`_record_passes_mesh_filters` 捕获所有异常并在 `over_limit_policy=skip` 时返回 `False`，导致路径错误、mesh 格式错误和 element 超限都表现为样本被跳过。

### 4.2 推荐最小改法

维护过滤统计：

```text
status_filtered
quality_filtered
missing_indicator
missing_stage_field
path_not_found
mesh_read_error
no_tetra
initial_size_out_of_range
target_size_out_of_range
retained
```

当 required split 为空时，错误中输出：

- 原始记录数。
- 每类过滤数量。
- 前 3 个失败样本 ID、字段和异常。

### 4.3 独立审计命令

建议增加只读命令：

```text
python audit_pipeline_dataset.py --root <pipeline_output_root> --config <task_config>
```

输出 JSON/CSV：

- schema 版本。
- split 和 geometry 重叠。
- 路径存在性。
- tetra 数量。
- indicator/stage-field 形状。
- quality/status 分布。
- 最终 retained 样本。

> **额外思考提醒：** 是否新增独立脚本，应根据现有 CLI 结构决定。如果 pipeline 已有适合的 validation 子命令，应扩展现有入口，避免重复实现两套审计逻辑。
> 这点需要你仔细阅读 tet_work/dataest-pipeline/ 源码后再次向我确认

## 6. 实验配置补齐

### 6.1 未加权 pipeline baseline

新增中文注释清晰的 run 配置，例如：

```text
amber_pipeline_baseline.yaml
```

必须与 weighted 配置保持：

- 相同 task 和 manifest。
- 相同 backbone。
- 相同 dataloader、epoch、optimizer、inference steps。
- 相同 mesh metrics。

只改变：

```yaml
algorithm:
  enable_physics_correction_branch: false
  weighted_imitation:
    enabled: false
```

指标仍可读取 physics importance 做评估，但不能参与 loss。

### 6.2 Feature-only 控制组

目标：模型共享编码器看到 stage field，但 final prediction 不使用 physics residual。

最小候选方案：

- 启用物理特征拼接。
- `gate_max=0`。
- correction aux/reg 权重设为 0。
- final 必须等于 expert prediction。

> **额外思考提醒：** 必须先确认当前 physics feature 是在共享 encoder 前拼入 `graph.x`。若是，则 gate=0 仍允许 expert head 使用 stage field，符合 feature-only 定义；若 feature 只进入 correction head，则该控制组无效，需要重新设计。应增加测试证明 feature 对 expert path 的可见性和 final=expert 的退化关系。

### 6.3 配置自检

每个实验启动时打印并保存：

- weighted enabled/source/mode。
- correction enabled。
- physics feature source。
- gate max。
- checkpoint init path。
- inference steps。
- retained split sizes。

## 7. 真实 PDE evaluator

### 7.1 最小职责

输入：

- 预测 mesh。
- manifest 中的 `condition_spec`。
- geometry/preprocess metadata。
- `reference_solution.npz`。

输出：

- PDE solve 是否成功。
- solution error。
- energy/H1 error或替代的 QoI error。
- mesh elements、budget ratio、runtime。

### 7.2 推荐复用

优先复用 pipeline：

- `solve_condition`。
- condition/preprocess record 构造。
- solution point evaluation。
- reference solution 文件。

不在 AMBER validation step 内运行昂贵 FE；采用 checkpoint 训练完成后的离线评估。

### 7.3 数值比较（这点须向我确认，能否在不修改模型架构的前提下实现?）

优先在固定公共 probe points 上比较 predicted/reference solution，避免直接比较不同 mesh 的节点数组。

如果实现 energy norm：需要验证梯度投影、体积积分和边界条件一致。

如果短期无法可靠实现 energy norm，保底输出：

- volume-weighted relative solution L2。
- condition-defined QoI relative error。
- solver success。

> **额外思考提醒：** PDE 指标定义是实验结论的核心创造性决策。不能仅因容易实现就选择某个误差。应检查 reference solution 是否真正比预测 mesh 解更精细、scalar cheap-reference 模式是否可作为可靠 ground truth、elasticity 的材料和边界 selector 是否能在预测 mesh 上一致重建。若 reference 不够强，应先修正 reference 协议。

### 7.4 测试

- reference mesh 与自身比较误差接近 0。
- 人为粗化 mesh 的误差通常高于 reference。
- 相同 condition 重复评估确定性一致。
- scalar/elasticity 都有至少一个 fixture。
- solver 失败写入状态，不产生伪造数值。

## 8. 结果落盘与聚合

建议每次运行保存：

```text
run_root/
├── resolved_config.yaml
├── code_version.json
├── dataset_version.json
├── checkpoints/
├── train_metrics.csv
├── val_metrics.csv
├── test_predictions/
├── per_sample_metrics.csv
└── aggregate_metrics.json
```

`code_version.json` 至少包含两个仓库 commit、dirty status 和运行环境。

`dataset_version.json` 至少包含 manifest hash、quality report hash、split 统计和过滤配置。

聚合器不得只读取 W&B 表格，应支持本地文件独立复现。
